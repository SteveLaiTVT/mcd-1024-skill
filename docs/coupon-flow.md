## 从可领到计价

1. 可领：`available-coupons` 返回展示，不提供可直接核价的已持有资产。
2. 持有：`query-my-coupons` 逐页读取，最多 5 页、每页 200；按资产 ID 去重，同名不同 ID 保留。
3. 适用：`query-store-coupons` 按门店与取餐方式查询，与卡包 ID/券码关联；校验启用状态、有效期和商品编码。
4. 分配：每张资产使用一次；多份同款套餐拆出一份使用一张券，保留原套餐子项。
5. 活动：读取 `campaign-calendar`，展示日期、范围与活动性质；关联同一券资产/规则码时校验星期、全天或限时窗口。活动的券信息不能替代持有证明。文章价格字段 0 不表示免费商品。
6. 核价：官方判断叠加和业务规则。拒绝、无折扣或更贵的方案不替换无券基准；零元报价可以有效。转盘引擎每份餐单最多比较 64 个方案，单餐券检查默认 16 个。报告截断/失败，不宣称全局最省；已含自动优惠的价格不会再次扣减活动折扣。
7. 预算：全部餐单完成比较，最终整单报价与人均预算 × 人数比较，再决定是否入盘。无券价超预算的餐单也要先尝试适用券。

名称类似、缺商品映射、期限不明、过期或未验证持有的券不直接定价。当前精确匹配套餐编码；券专属商品的自动替换尚待真实持券样本接入。

## 领取

`auto-bind-coupons` 领取全部，没有单张参数。扩展页面先展示“领取全部可领券”确认窗口；打开或取消窗口都不写入，确认后才发送一次。连接、查券与生成转盘不会自动领券。研究脚本的显式 `--claim-all` 入口保留，但本次未执行。

领券请求不自动重试；响应不明确时报告未知，禁用再次领取，先由用户主动刷新券包核对，不把请求发出当成成功。成功响应后也要重新查询券包、门店范围与活动，并重新核价后才启用转盘；领取成功数量不能证明当前餐单适用。重复点击和旧异步响应不能造成重复领取或恢复已断开的账号。

## 证据

真实验证覆盖可领取列表、空卡包、空门店券和 22.90 元单人套餐核价。测试覆盖同名不同资产、重复展示、过期/禁用/未知期限、数量拆分、单券唯一使用、编码匹配、报价拒绝、无优惠、零元报价和领券不重试。真实持券折扣成功案例仍待验证。

券编号只在内存中参与请求，报告只展示名称、计数和价格，不输出券 ID、券码或支付链接。

当前页面和统一核价入口是 `web/app.js` / `web/meal-engine.mjs`，MCP 客户端为 `web/mcp-client.mjs`。Token 默认留在当前应用页内存，可自行勾选本机长期保存，取消勾选或主动断开删除记录。券资产始终只在本页内存，断开或退出清除。刷新恢复连接和已重新确认的门店，不恢复旧券包或报价。`serve_wheel.py` 仅预览静态历史体验，不接收 Token，也没有业务 API。条件变化或报价过期后不能使用旧转盘。
